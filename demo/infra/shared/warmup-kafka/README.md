# Autonomous warm-up Kafka image

This image wraps the pinned official `docker.io/apache/kafka:4.3.1` broker with a
continuous topic reconciler. It is an optional transport for protocol-v6 traffic
warm-up; the application still owns no topic-creation privileges.

```bash
docker build -t ckc-perf/warmup-kafka:latest demo/infra/shared/warmup-kafka
docker run --rm --name ckc-warmup-kafka -p 19092:9092 \
  -e KAFKA_BOOTSTRAP_TOPICS='ckc.traffic-warmup.v6.control, ckc.traffic-warmup.v6.order.events,ckc.traffic-warmup.v6.batch.events,ckc.traffic-warmup.v6.cauldron.events' \
  -e KAFKA_ADVERTISED_LISTENERS=PLAINTEXT://localhost:19092 \
  -e KAFKA_AUTO_CREATE_TOPICS_ENABLE=false \
  -e KAFKA_NODE_ID=1 \
  -e KAFKA_PROCESS_ROLES=broker,controller \
  -e KAFKA_CONTROLLER_QUORUM_VOTERS=1@localhost:9093 \
  -e KAFKA_LISTENERS=PLAINTEXT://:9092,CONTROLLER://:9093 \
  -e KAFKA_LISTENER_SECURITY_PROTOCOL_MAP=PLAINTEXT:PLAINTEXT,CONTROLLER:PLAINTEXT \
  -e KAFKA_INTER_BROKER_LISTENER_NAME=PLAINTEXT \
  -e KAFKA_CONTROLLER_LISTENER_NAMES=CONTROLLER \
  ckc-perf/warmup-kafka:latest
```

`KAFKA_BOOTSTRAP_TOPICS` is required. The reconciler trims whitespace, removes
duplicates, creates only missing topics with one partition and replication factor
one, and never deletes topics or changes their partition count. A topic with any
other partition count keeps readiness closed and is reported as
`incompatible_metadata`.

Readiness is based on a fresh successful reconciliation, not a marker retained
from an earlier broker lifetime. The following settings are optional:

| Variable | Default | Meaning |
| --- | --- | --- |
| `KAFKA_RECONCILE_INTERVAL_SECONDS` | `5` | Verification period |
| `KAFKA_RECONCILE_BACKOFF_SECONDS` | `2` | Retry delay after an unavailable broker or invalid metadata |
| `KAFKA_OPERATION_TIMEOUT_SECONDS` | `10` | Bound for every Kafka CLI operation |
| `KAFKA_READY_MAX_AGE_SECONDS` | `15` | Maximum accepted age of the last complete verification |
| `KAFKA_SHUTDOWN_TIMEOUT_SECONDS` | `30` | Grace period before child processes are killed |

The Kubernetes deployment generated by the shared experiment orchestration uses
the same image and a stable `ckc-warmup-kafka` Service. A broker exit or unexpected
reconciler exit terminates the container so Kubernetes can restart the complete
supervised unit. Full loss of the ephemeral broker data therefore creates a new
Kafka log at the same address; CORE-83 deliberately terminates old sessions and
allows new sessions after topic reconciliation.

Internal-lab experiments opt in through their environment configuration. The
topic list is materialized into `KAFKA_BOOTSTRAP_TOPICS`; changing it does not
rebuild the image.

```yaml
environments:
  internal-lab:
    lab: {profile: installed}
    warmup_kafka:
      enabled: true
      placement: application
      topics:
        - ckc.traffic-warmup.v6.control
        - ckc.traffic-warmup.v6.order.events
        - ckc.traffic-warmup.v6.batch.events
        - ckc.traffic-warmup.v6.cauldron.events
```

Complete standalone manifests are in [`examples/docker-compose.yml`](examples/docker-compose.yml)
and [`examples/kubernetes.yaml`](examples/kubernetes.yaml). The internal-lab
preparation waits at most 120 seconds for initial transport readiness and then
starts the application anyway, allowing the core cold-fallback path to run.

The bounded Docker lifecycle qualification can be run against any built tag:

```bash
demo/infra/shared/warmup-kafka/tests/container-lifecycle-test.sh \
  ckc-perf/warmup-kafka:latest
```

It verifies record-preserving restart, incompatible partition metadata, automatic
topic restoration after deleting the broker data volume, and supervisor response
to an unexpected reconciliation-process exit. Its trap removes the temporary
container and volume on success, failure, or interruption.
